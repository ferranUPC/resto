# DEV-NET/peak scenario matrix

Work-plan E3.1, architecture doc §3: "ground truth for counterfactuals; experiment store for the
learning-effect experiment". 20 `Scenario` rows on DEV-NET's `peak` demand profile, each simulated
at 3 seeds (60 `SimulationResult`s total), stored through the real DatabaseMCP contract.

## Build it

```bash
conda activate resto
# SUMO_HOME must be unset (CLAUDE.md)
python -m eval.scenario_matrix.build
```

Idempotent: `build_scenario`/`run_simulation`/`scale_demand` all dedupe on content/request
hashes, so a re-run after the first successful one touches no SUMO process again ("zero redundant
simulations") and finishes in a couple of seconds. Deleting `matrix.db` and `runs/` first forces a
full rebuild from scratch.

## What's here

- `rows.py` — the 20 `MatrixRow` specs and `build_draft`, which turns one into a `ScenarioDraft`
  using the same deterministic writers (`RerouterWriter`/`VssWriter`/`TlsProgramWriter`,
  `scale_demand`) the Scenario Builder agent's tools call — no LLM involved, these are
  hand-authored ground truth, not a Builder-bank grading run (that's E2.7).
- `tls_alt_program.py` — generates the alternate `tlLogic` program each `signal_program` row's
  WAUT switches to, by retiming (not redesigning) the junction's own `programID="0"` phases.
- `build.py` — orchestrates the build: promotes every row through the real `build_scenario`/
  `run_simulation` use cases, stores through `DatabaseMCP` proper (a real MCP `ClientSession`,
  not the repository classes called in-process), re-checks each row's own DoD §4.5 effect against
  its seed-1 result (`verify.effects`, E2.4) before it counts as built, and writes
  `matrix-report.md`.
- `matrix.db` — the `SqliteDatabase` reference backend, **committed**: the durable asset. Every
  `Scenario`/`SimulationResult` (interventions, mechanisms, KPIs, content hashes) is inline JSON
  in this file — no separate data store needed to read the matrix back.
- `matrix-report.md` — **committed**, human-readable summary (one row per scenario, mean KPIs
  across the 3 seeds).
- `runs/` — **gitignored** (~140 MB): the raw per-row SUMO artifacts (`sumocfg`, additional
  files, `edgedata`/`tripinfo`/`statistics`/`summary`). Regenerated by `build.py`; `matrix.db`'s
  own `ArtifactRef`s point here by absolute path (the project-wide convention — see
  `adapters/persistence/filesystem.py` — every artifact ref is an absolute path, not portable
  across machines). On a fresh clone, `matrix.db` alone still gives every KPI and identity; only
  re-reading a specific raw output file (e.g. re-parsing `edgedata` by hand) needs
  `python -m eval.scenario_matrix.build` run once to regenerate `runs/`.

## Coverage

Every mechanism E2.2/E2.3 actually implement: `baseline` (1), `lane_closure` (4), `edge_closure`
(4), `speed_limit` (4), `signal_program` (4), `demand_scale` (3, factors 0.8/1.2/1.5). The
architecture doc's own example matrix rows S05 (`condition` script) and S06 (derived network)
need E2.6 and E6.1 respectively, neither of which exists yet — out of scope here by construction,
not an oversight.

Every `lane_closure`/`edge_closure`/`speed_limit` row's window is `[0, 300)` — found empirically
while first building this matrix (see `rows.py`'s own docstring): a later window in the hour-long
`peak` run can have a vehicle already mid-edge when the window opens, which the edgedata-based
effect check cannot distinguish from the closure not working. Diversity across these rows comes
from location (5 named DEV-NET edges) and mechanism, not window offset. `signal_program` windows
are unrestricted, since those rows are not edgedata-checked.
