## An agent got deleted, and that is good news

Last review I flagged E5.2 (the Coordinator/Planner agent) as the real risk under M3. An LLM agent that
has to route and plan from a live model is a different kind of task from the rules-and-schema work that
had been going fast, closer to E5.1's Parser tuning, which took six prompt versions and still missed
its own bar. I said I would not extrapolate that week's velocity onto E5.2 without discounting it.

r13 made that discounting moot by deleting the thing I was discounting. ADR-0039's argument holds once
stated. After ADR-0037 (no database tools) and ADR-0038 (the contrast fixes the arms), the Coordinator
had no decision left to make that code did not already decide. So it is not an agent anymore. It is
`domain/services/planner.py::plan_study`, a pure function tested against 14 hand-frozen oracle plans
plus properties and a metamorphic test. I checked that this is not a renaming exercise.
`CoordinatorAgent`, `ClarificationRequest` and the `coordinator.py` placeholders are actually gone from
`src/`, not aliased or soft-deprecated. E5.2 and E5.5 are cancelled, not postponed, and their pieces
(the oracle, the trace checks, the failure classification) already exist or have a named new owner.

This is the right engineering call, and I want to flag the one place it is not free. A thesis whose
premise is "agentic traffic simulation" now has one fewer agent than its own architecture table still
claims. `tfm-architecture-and-dod.md` §2.4 still lists Coordinator as a live row (E5.15, still ⬜,
exists specifically to catch that). Five agents remain genuinely agentic: Network Author, Demand
Generator, Scenario Builder, Network Expert, Output Composer. The sixth is now deterministic code with
an LLM agent's old name retired. That is a defensible design decision, arguably a stronger one.
ADR-0039 argues it correctly, and a function that cannot hallucinate a plan is better for M3's
reliability bar than an agent that might be wrong. But it changes what "the Coordinator" means in the
thesis text, and nobody has written that framing down yet. I would settle it in E10.2 rather than let a
reviewer notice the gap between the architecture diagram and the delivered system.

## Risks actually observed this review

1. **E3.7's review target keeps moving under it.** Last review I called the plan-bank review ready to
   review. It is not anymore, not because anyone regressed it, but because r9 and r13 regenerated the
   plans through the new planner and intent rules, and 30 of the 54 plans now differ from the snapshot
   the maintainer would have been reviewing against. The project built a real tool to track this
   (`reviewed_snapshot.json` and `annotation/changes.py`), which is the right response, but it does not
   change the fact that every refactor touching the planner before the review happens adds re-review
   work. The fix is not more tooling. It is doing the review soon, before the next refactor moves the
   target again.
2. **The evaluation budget has a stated, not hidden, overrun risk.** E3.9's own numbers say the "planned"
   tier reaches $20.58-32.47 combined (V1+V2, with contingency) against the $30 reference, over by up to
   $2.47 at the high end. The document states this plainly ("that possible excess is what the funding
   request can ask for"), which is the correct way to present it to supervisors. But the ~24 Oct funding
   request is doing real work here, not clearing a formality. The project is asking for headroom it may
   actually need.
3. **E3.10 is drifting the wrong way.** It is a small, deadline-flexible task (2 pts, due 11 Dec), but
   it went from about 35 untrimmed entries to 72 lines in a file that was supposed to shrink. Not
   urgent, but worth noting that letting documentation debt sit on the assumption that a later "trim"
   task will absorb it gets more expensive the longer it waits, as this review's own check shows.

## Recommendation

Keep going as planned. Nothing here calls for any step of the §5 fallback order. If anything, today's
refactor removed risk from the plan rather than adding it. Two concrete asks, neither a plan change. Get
the E3.7 plan-bank review done before the next planner-touching refactor makes it 40 of 54 instead of
30 of 54. And write E10.2's framing of what the Coordinator/Planner is now, before that gap sits in the
thesis text unaddressed for months.
