## Verification this review actually did

This container has no `resto` conda env (as expected — noted in the run instructions), so the
skill's fallback path was used: dependencies were installed directly with `pip` against the
system Python 3.11.15. This worked — the container does have outbound network access to PyPI —
but hit one real snag worth recording: a `pip install -e ".[dev]"` failed partway through because
it tried to uninstall a Debian-packaged `PyJWT` that has no pip `RECORD` file, aborting the
transaction before `mcp`, `pydantic`, `openai`, and their pins ever installed. Re-running with
`pip install --ignore-installed PyJWT -e ".[dev]"` fixed it and pulled in the full stack
including `eclipse-sumo`/`sumolib`/`traci` 1.27.1. This is a property of this particular cloud
container's base image, not of the project — but it means a truly cold environment needs that
flag (or a venv) to install cleanly, which isn't documented anywhere in the repo today.

With the environment installed:

  artifact of this container never having run the demand-generation notebook, not a regression.
  638 vs. the 639 the 18 Sep review reported is fully explained by that one now-skipped case;

3. **Environment fragility, minor:** this run's `pip install` snag (Debian `PyJWT` blocking the
   editable install) is a container quirk, not a project defect, but a one-line note in the README
   about `pip install --ignore-installed PyJWT -e ".[dev]"` (or recommending a venv) for anyone
   without the `resto` conda env would remove friction from future unattended runs of this same
   review.
