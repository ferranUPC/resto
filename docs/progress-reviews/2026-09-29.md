# Feasibility analysis, 2026-09-29

## Where things actually stand

One day and nine commits since the last review (`c7a54d2`, 2026-09-28), and none of them move a
tracker row. Six commits (`f2d73bc` through `974b933`) pull the Executor, already done under E5.10, out
of a single 955-line `run_study.py` into a nine-module `application/executor/` package, recorded as
ADR-0030. Every one of those commit messages says "no behaviour change," and I believe them: the same
`test_run_study.py` suite that covered the GP-1/GP-2/GP-3-shaped scenarios before the split still covers
them after it, plus new module-local tests (`test_failures.py`, `test_plan_validation.py`). The other
three (`258b4b8`, `e064862`, `644717f`) plus `0224bdb` add a committed price manifest
(`config/prices.toml`) that makes an unpriced model a hard `UnknownModelError` instead of a silent
`None`, and `eval/paid_runs.py`, a shared cost-capped job runner that `expert_benchmark`,
`parser_benchmark`, and `hygiene_probes` all now go through instead of three separately-written loops
with their own cap logic. I re-ran the suite from a fresh `pip install -e ".[dev]"` (no `resto` conda
env in this container): 964 passed, 1 skipped (same pre-existing fixture gap as every prior review),
`ruff check .` clean, and `mypy` clean over 275 files when invoked the way the project's own
`pyproject.toml` intends (bare `mypy`, which reads its `files` list). Running it as `mypy .` instead
walks the whole tree and surfaces 7 errors in `eval/dev-net/demand/sim_utils.py`, a file the config
excludes on purpose (comment: "never written against mypy, fixing its untyped ElementTree navigation is
a separate task"). That is not a regression, just a config subtlety worth remembering for the next
review that reaches for `mypy .` directly.

Both pieces of work are real and competently done. Splitting a 955-line god-module into
responsibility-scoped files with matching tests is the kind of thing that pays off the first time
someone has to change one phase's failure handling without rereading the whole class. A shared,
cap-enforcing job runner with resume-by-key and a hard per-model price check is exactly the safety net
you want before spending real money against a fixed $30 evaluation budget. The last three reviews ran
paid sweeps ($0.99, $0.28, $0.32, $0.056, $0.112, among others) through three separately hand-rolled
loops, and folding them into one audited module removes a class of "did I remember the cap in this one
too" mistakes before Validation 2 needs to run larger versions of exactly these jobs. Neither commit set
invents progress that isn't there, and neither claims a task is more done than it is.

## Bottleneck observed this review

Not a technical one this time. The diagnostic Jaccard risk flagged last review is unchanged and still
correctly logged as an accepted, costed risk for Validation 2. The bottleneck this review surfaces is
sequencing: engineering-quality work (a refactor, a shared cost-safety module) keeps getting picked up
ahead of the unstarted build tasks that actually gate M3 and M5, even in a week where the tracker itself
names those tasks as unblocked and due. That is a defensible call in isolation: nobody wants to build
the Coordinator agent on top of a 955-line module they're about to want to change anyway, and nobody
wants to run V2-scale paid sweeps through three unaudited loops. But it is now two reviews in a row
where the stated next action did not happen, and I would want to see E3.7 or E6.3 actually start before
reading a third skip the same way.

## Recommendation

**Keep going as planned. No §5 fallback step is warranted, but the concrete action for next session is
non-negotiable this time: touch E3.7 or E6.3, not more refactoring.** Both are wave-1b tasks with no
remaining external blocker, both are five-plus weeks from their targets rather than in immediate danger,
and both are exactly the kind of task that a string of "useful but adjacent" days keeps deferring. The
project has almost seven months of total slack per the note in the review skill itself, so this is not a
crisis; it is a pattern worth naming honestly before it becomes one that does put M3 or M5 at risk.
