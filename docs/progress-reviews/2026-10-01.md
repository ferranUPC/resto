# Feasibility analysis, 2026-10-01

## Where things actually stand

Sixty-nine commits landed on 2026-09-30 since the last review (`8a375bc`), the single heaviest day
of commit activity any review has seen so far. I read through the diffs and the ADRs rather than the
commit log alone, because a day this size is exactly where a shallow pass would miss what actually
moved. Three threads matter; the rest is refactor cleanup or project tooling.

First, ADR-0032 (Expert network scope) went from Accepted to built. `ExpertTask` now carries a
`network_ids` scope instead of one id, every topology tool and `search_notes` check their argument
against it through a new `NetworkQueryLoader` port, and a note's network is derived by code from its
scenario instead of chosen by the note writer. I grepped the repo for `TODO(E5.3)`, the marker the
tracker has cited for a week as the open multi-network risk, and it is gone, not just moved. That
retires a named risk on E5.3, E6.7 and M4 ahead of when any of those tasks needs it.

Second, Expert tuning moved from v4 to v6 on the diagnostic family, and the result is a genuine
de-risk, not cosmetic progress. v4 sat on the Jaccard ≥0.6 bar with, in the maintainer's own words,
zero margin, and the last two reviews both repeated that as an accepted, unresolved risk. v6
(`get_tls` answers an unknown id instead of raising, so the Expert stops splitting lookups one call
at a time) scores Jaccard 0.95 and cause accuracy 0.93 on the same 1-repetition, 20-question sweep.
That is still development evidence, not a Validation-2 result, but it changes what I would have
written about E4.3's risk profile yesterday. The newest version, v7, only changes the network-scope
plumbing (ADR-0032) and has not been swept at all, so whether it holds v6's score is still an open
question EXP-01 will answer, not this sweep.

Third, and the one I only found by reading the ADR text rather than the commit messages: ADR-0035
(described demand, E3.11) states in its own context section that it was "found while triaging E3.7".
The maintainer opened the plan-bank task, found that the Coordinator has no rule for choosing between
DEV-NET's three same-window demands, and built the fix (`Demand.description`, `labels`, no silent
fallback) rather than plan bank itself. `eval/plan_bank/` still does not exist, so E3.7 is not
started in the tracker's own terms, but this is the first evidence since 2026-09-23 that anyone
touched it at all, and it reads differently from three reviews of "the critical chain had zero
commits." The gold-plan-bank work can only be built once demand resolution has a rule, so fixing that
gap first is the task, not a detour from it. I added E3.11 as a new 🔄 row; its own scope
(request-bank concepts, the Parser's prompt, `network_only`) is still open, so it is not done.

The test suite grew from 992 to 1261 passed with zero regressions, `ruff` and `mypy` both clean
(310 source files, up from 286). I rebuilt the venv from scratch this session, and unlike the last
two reviews, `pip install -e ".[dev]"` worked on the first try with no `PyJWT`/`cryptography`
conflict to route around. That is a container-provisioning note, not a repo finding.

## Pace vs. the v0.3 calendar

I want to walk back part of what the last three reviews said, now that I have checked it against the
plan's own wave boundaries instead of a vague "a week is a long time" instinct. Wave 1a (E3.8 →
E5.13 → E4.2-E4.4 dev sweeps) was entirely done by 2026-09-25, two weeks ahead of its 9 Oct target.
Wave 1b (E3.11 → E3.7 → E5.2 → E5.3 → E5.4 → E7.1, with E6.3 "in the gaps") does not start, by the
plan's own calendar, until 12 Oct. So the "zero commits on E3.7" complaint of the 09-28/09-29/09-30
reviews was measuring the project against a start date eleven days before the plan calls for it. That
does not mean the complaint was baseless. The plan explicitly says E6.3 has no prerequisite and can
fill the gap now, and today shows the maintainer can pull wave-1b work forward when something
concrete prompts it, as E3.11 did when the maintainer actually opened E3.7. But the last three
reviews' framing read "idle" as a lateness signal rather than banked slack being spent at the
maintainer's own discretion, inside a plan built with roughly 158 points of exactly that slack.

What is still true, and still the one piece of free time sitting on the table: E6.3 (REAL-NET
freeze) has had zero commits since the project started, no `real-net.*` file of any kind exists, and
it has no prerequisite at all. It could start today independently of everything else. Every week it
sits idle is a week subtracted from M4's 15 Jan deadline and M5's chain (E6.3 → E6.6 → E3.5 → E3.6 →
E4.8, 60 points), since nothing else feeds it and nothing blocks it. This is a narrower version of
the standing recommendation. Not "touch the spine", which today's work shows is already happening
through E3.11, but specifically E6.3, which nothing is currently touching and nothing needs to finish
before it can.

One date worth flagging on its own clock, independent of the build waves: E3.9 (the evaluation
budget document for the supervisors) is due "before the ~24 Oct funding request", 23 days out, and is
still ⬜ with no `docs/*budget*` file in the repository. It is a small task (5 points) with an
external, fixed deadline rather than an internal target, which makes it a different kind of risk than
the build-wave tasks. Worth a line in whatever planning happens next, not yet worth raising further.

  before EXP-01 runs in V2.
- **M3** (end-to-end loop built). Still needs E3.7, E5.2, E5.3, E5.4 at ✅ plus GP-1…7+9. E3.11 moving
  to 🔄 and E5.3's multi-network risk closing are both real movement on the chain feeding this
  milestone, but none of E3.7, E5.2, E5.4, E7.1 has a single commit yet. Target is 6 Nov, five weeks
  out. Per the wave calendar this is still on schedule, not at risk, since wave 1b's window
  (12-23 Oct) has not opened yet.
- **M5** (thesis result built). Unchanged, and this is the one I am most willing to call a genuine,
  avoidable gap rather than a scheduling artifact. E6.3 has no plan-calendar excuse for being
  untouched, and it feeds a 60-point chain with a 4 Dec target, nine weeks out but with four
  sequential tasks ahead of it (E6.6, E3.5, E3.6, E4.8) that cannot start until E6.3 freezes.

## Recommendation

Keep going as planned. Nothing here calls for any step of the §5 fallback order on points, dates, or
quality. I am revising, not repeating, the last three reviews' framing: the Coordinator spine is
moving, just not in the form of a finished E3.7, and that is a reasonable way for triage-driven work
to look. The one concrete, low-risk ask that stands on its own regardless of wave boundaries is E6.3.
It has no prerequisite, no technical risk anyone has identified, and a real downstream chain waiting
on it. If the next review can report a `real-net.*` file and a fix log, that closes the one piece of
schedule risk this review found that is not simply "not due yet."
