The eighth, `d72f880` (ADR-0031), is not a refactor. It is a real bug fix, and worth reading
carefully rather than waving through as more hardening. `result_id` is computed from
`(scenario_id, seed, mode, sumo_version)` before SUMO runs, so a retried seed reuses the same id.
`SqliteResultRepository`'s idempotency check treats a second `store` under an existing id with
different content as a corrupted store and raises `ConflictError`. That check is correct for a
genuinely deterministic result but wrong for a `failed` one, since `status`/`kpis`/`error`/
`wall_clock_s` will almost always differ between a failed attempt and the successful retry that
follows it. Before this commit, any real study that failed a seed and retried it would have crashed
the moment it tried to store the successful rerun, on the SQLite backend the CLI actually wires, not
the in-memory one most tests use, which is exactly why nothing caught it until now. The fix stores
only `ok` results, stages each attempt in its own directory, and promotes it to the canonical path on
success. That is a sound design; I checked the ADR's alternatives section, and versioning `result_id`
by attempt was rejected for the right reason, since it would defeat "zero redundant simulations". I
confirmed the Executor's `steps.py` was updated to pass its own `attempt` label into the new required
parameter, so this is not a change that landed underneath the Executor without the caller catching
up. This is the kind of bug that would otherwise have surfaced expensively, in the middle of
Validation 2, on a paid run that happened to fail a seed.

I re-ran the suite myself rather than trusting the commit messages. `pytest -q` gives 992 passed, 1
skipped (up from 964; the skip is the same pre-existing fixture gap every review has noted),

## Bottleneck observed this review

Same one as last time, now sharper: sequencing, not a technical blocker. Two reviews in a row named
the same next action, start E3.7 or E6.3, and it did not happen either time. Instead the maintainer
picked up a refactor and, credit where due, found and fixed a real bug along the way. I do not think
this is drift or avoidance. ADR-0031 is a legitimate, well-reasoned fix, and nobody should feel bad
about fixing a crash they found. But "found while working on something else" is not a plan, and the
plan's own critical-path warning exists precisely so that adjacent-but-not-critical work does not
keep winning by default. The diagnostic Jaccard risk (E4.3, accepted with zero margin) is unchanged
and still correctly logged, not re-litigated here.

## Recommendation

Keep going as planned. No §5 fallback step is warranted on points or dates. But the standing
recommendation now needs teeth: the next commits should be against E3.7 or E6.3, not more
refactoring or incidental bug fixes, or this stops being a pattern worth naming and starts being the
actual velocity of the critical chain. Both tasks are wave-1b, both have no external blocker left, and
both sit five-plus weeks from their nearest target. There is no crisis yet, and the plan's own ~170-pt
slack backs that up. What has changed since the last two reviews is confidence: I can no longer read a
week of adjacent work as an isolated, defensible choice. If a fourth review in a row opens with "the
critical chain still hasn't moved," that is the point to stop calling it a pattern and start treating
it as the plan's real trajectory.
